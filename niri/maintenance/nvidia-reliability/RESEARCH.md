# Source review and implementation rationale

Reviewed 2026-10-10 against the installed Fedora 45 packages. Recommendation: omit the versioned NVIDIA modules from early userspace and load the matching open modules on the real root after akmods has finished. Add explicit boot preparation because this machine is pinned to NVIDIA and its older installed kernel already has stale on-disk modules.

## Evidence

**NVIDIA requires matching releases.** NVIDIA's own open-module README requires corresponding kernel modules, GSP firmware, and userspace. The supplied 615.71.09/615.78.08 logs show both missing old firmware and an API mismatch. Moving a stale copy out of the initramfs eliminates one independent source of version skew. [NVIDIA README](https://github.com/NVIDIA/open-gpu-kernel-modules#how-to-build)

**RPM Fusion intentionally omits NVIDIA.** Its shipped `99-nvidia-dracut.conf` omits the four main modules to avoid regenerating the image on driver updates. The local `add_drivers` setting forces inclusion despite that policy. The replacement local file removes those additions and explicitly omits all five NVIDIA modules, preserving nouveau omission. [RPM Fusion source](https://github.com/rpmfusion/xorg-x11-drv-nvidia/blob/master/99-nvidia-dracut.conf)

**Dracut supports a safely staged build.** Its configuration defines `add_drivers` and `omit_drivers`; command-line options control output image, kernel, configuration directory, and ordinary versus UEFI image generation. The locally installed dracut 111 script still merges distribution configuration when `--confdir` selects the staged local directory. Candidate archives are inspected before any active images are replaced. [Configuration documentation](https://dracut-ng.github.io/dracut/man/dracut.conf.5.html), [Command documentation](https://dracut-ng.github.io/dracut/man/dracut.8.html)

**Akmods has multiple update/boot paths, and timing alone is insufficient.** Fedora bug 2379766 documents the installed-but-not-running kernel version mismatch and the need to unload an already-loaded old driver. The fix restored building for the current and default kernels on driver updates; it did not turn all installed kernels into guaranteed synchronized fallbacks. This review found 615.71.09 for kernel 7.2.8 while kernel 7.2.9 has 615.78.08. [Fedora bug and maintainer explanation](https://bugzilla.redhat.com/show_bug.cgi?id=2379766#c10)

The installed `/usr/sbin/akmods` from `akmods-0.6.2-14.fc45` confirms that `--from-init` handles the running kernel, normal update handling checks running/default kernels, builds use a lock, and successful builds retrigger aliases. Its service is already enabled and ordered before `display-manager.service`. The kernel-specific service runs inside a shutdown inhibitor. Critically, the script can end successfully despite a per-module build failure, so the custom helper inspects installed modules after a repair instead of trusting the exit code alone. These findings come from the installed package source, not an assumption about older tutorials.

**Alias blacklists allow explicit loading.** Kmod documents `blacklist` as suppressing a module's internal aliases; `--use-blacklist` also applies that policy to module names and is used by udev. The helper explicitly requests `nvidia_drm` without that flag after checking package versions, signing metadata, and firmware. A dry run using this machine's installed kmod verified both behaviors. This resolves the possibility of the old on-disk module loading while the boot-time build is still underway. [modprobe.d documentation](https://github.com/kmod-project/kmod/blob/master/man/modprobe.d.5.scd), [modprobe documentation](https://github.com/kmod-project/kmod/blob/master/man/modprobe.8.scd)

**Secure Boot checks signatures regardless of the source filesystem.** The kernel verifies module signatures when loading. Omitting a module from the initramfs does not disable that verification. The helper checks the already-enrolled certificate and module signing identifier; the final explicit load remains subject to the kernel's cryptographic verification. The installer contains no key-generation, enrollment, or firmware-configuration commands. [Kernel module-signing documentation](https://docs.kernel.org/admin-guide/module-signing.html#loading-signed-modules)

**Local systemd configuration survives updates and can preserve recovery.** Systemd documents administrator drop-ins under `/etc` and their precedence over vendor configuration. `Wants` combined with `After` orders preparation without preventing GDM startup when preparation fails. The guard is additionally ordered before RPM Fusion's nouveau fallback so fallback does not race a successful explicit NVIDIA load. [systemd unit documentation](https://github.com/systemd/systemd/blob/main/man/systemd.unit.xml), [RPM Fusion fallback service](https://github.com/rpmfusion/xorg-x11-drv-nvidia/blob/master/nvidia-fallback.service)

**Niri can use a render-device path tied to PCI identity.** Niri 26.04 opens the configured path and identifies the DRM node, rather than requiring the literal numbered filename. Systemd's DRM rules create PCI-based render-node links. Pinning the GPU by PCI address avoids a device-number change caused by different probe order. The modified configuration parses with the installed binary; actual link availability is checked by the boot helper. [Niri 26.04 source](https://github.com/niri-wm/niri/blob/v26.04/src/backend/tty.rs), [Systemd DRM rules](https://github.com/systemd/systemd/blob/main/rules.d/60-drm.rules)

## Why not the alternatives

- **Rebuild the initramfs after every driver change:** valid for a machine that needs early NVIDIA graphics, but requires correct handling of both kernel and driver updates after successful builds. This unencrypted machine can avoid that extra synchronized copy entirely.
- **Edit vendor akmods units:** those edits can be replaced by packages. This implementation leaves vendor units untouched.
- **Only change niri's GPU preference:** useful for probe numbering, but cannot restore a GPU that failed firmware initialization or solve the NVIDIA API mismatch.
- **Force hot unloading or automatic reboot:** could disrupt the active desktop. Neither is used.
- **Disable Secure Boot, replace the signing key, or regenerate GRUB:** unnecessary for this failure and outside the user's constraints. None is used.

The managed loading service is a custom integration derived from these sources. It has local failure-case tests; it is not represented as a vendor-supported automatic recovery feature. Full host verification and a subsequent ordinary boot are still required.

**Mokutil output must be interpreted explicitly.** The first host run stopped in preflight because the installed mokutil reported the existing certificate as already enrolled with a nonzero exit code. Upstream also allows zero-status outcomes for pending enrollment or blacklists. The corrected check accepts only the exact certificate-specific enrolled/in-db message, with no additional errors, and does not make enrollment requests. Regression tests cover both exit conventions and reject pending/blocked/read-failure results. [Mokutil implementation](https://github.com/lcp/mokutil/blob/master/src/mokutil.c)

**PKCS#7 `modinfo sig_key` is the certificate serial.** Kmod obtains this field from the signature's issuer-and-serial structure, not the X.509 subjectKeyIdentifier extension. The second host attempt exposed the incorrect comparison in the initial helper; it stopped before image/configuration replacement. The fixed check compares `openssl x509 -serial` with normalized `modinfo sig_key` and requires PKCS#7 metadata. A public export of the actual enrolled akmods certificate has serial `37B742E07FF3F05332CB806DB699A393908BC9D3`, matching all four checked modules on both installed kernels. [Kmod PKCS#7 parser](https://github.com/kmod-project/kmod/blob/master/libkmod/libkmod-signature-openssl.c)
